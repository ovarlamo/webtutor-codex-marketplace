# Ключевые правила для LLM, пишущей код WebTutor

> **Главный тезис:** SP-XML Script — отдельный язык. Он синтаксически похож на JavaScript, но его типы, коллекции, объектная модель, библиотеки, запросы и среда выполнения устроены иначе.

Этот блок нужно прочитать до генерации или ревью любого `.js`-файла, исполняемого WebTutor.

## 1. Не считать SP-XML браузерным или серверным JavaScript

Не предполагать наличие DOM, `window`, Node.js API, npm-пакетов, CommonJS/ES modules, `Promise`, `async/await`, стрелочных функций, `let`, `const`, destructuring или spread. Использовать современную конструкцию можно только после подтверждения ее поддержки установленной версией WebTutor.

Консервативный совместимый стиль проекта: `var`, обычные `function`, простые объекты, платформенные функции и библиотеки через `OpenCodeLib()`.

**Универсальное обязательное правило:** тернарное выражение, используемое как
значение свойства объектного литерала, заключать в круглые скобки. Правило
подтверждено в WebTutor 2025.2.1403, но не ограничено этой версией. Без скобок
парсер может сообщить о синтаксической ошибке только на следующем свойстве:

```javascript
var dto = {
    value: (field.HasValue ? OptInt(field) : null),
    code: String(code)
};
```

Для наиболее консервативного кода допустимо заранее вычислить значение обычным
`if` и затем передать готовую переменную в объект.

### Не объявлять `var` внутри циклов

**Универсальное обязательное правило:** внутри тела любого цикла не должно
быть ни одного объявления `var`, в том числе во вложенных `if`, `try`/`catch`
и `switch`. Все рабочие переменные объявлять один раз до входа в цикл, а внутри
цикла только присваивать им значения. Поведение подтверждено в WebTutor
2025.2.1403, но правило не ограничено этой версией. Повторное выполнение объявления на
следующей итерации может завершиться ошибкой `Variable <name> already declared`.

Неправильно:

```javascript
for (item in items)
{
    if (item != null)
    {
        var found = ArrayOptFind(result, "This.id == item.id");
    }
}
```

Правильно:

```javascript
var found;
for (item in items)
{
    found = null;
    if (item != null)
    {
        found = ArrayOptFind(result, "This.id == item.id");
    }
}
```

## 2. Не полагаться на JS-приведение типов

**Официально:** `undefined`, `null`, пустая строка, `0` и `false` — разные значения; сравнение строгое. `Integer` и `Real` — разные типы. Строка и дата прежде всего скалярные значения, а не JS-объекты.

Практическое следствие:

```javascript
if (value == undefined || value == "")
    value = default_value;

var id = OptInt(raw_id);
if (id == undefined)
    throw Error("Некорректный идентификатор");
```

Проверять именно те пустые состояния, которые допустимы контрактом. Не заменять такую проверку на `if (!value)`.

## 3. Различать байты и символы

**Официально:** строки бинарно-совместимы и хранят текст в кодировке приложения, обычно UTF-8. `StrLen()` возвращает число байтов, `StrCharCount()` — число символов. Аналогично, байтовые `StrLeftRange()` и символьные `StrLeftCharRange()` решают разные задачи.

Для пользовательского текста выбирать функции с `Char` в названии. Байтовые функции использовать только когда действительно обрабатываются байты, кодировка или бинарное содержимое.

## 4. Не считать все коллекции JS-массивами

**Официально:** кроме стандартного массива существуют абстрактные массивы. `for-in` по стандартному объекту перебирает имена свойств, а по абстрактному массиву — значения, то есть ведет себя как `foreach`.

Перед обработкой неизвестной коллекции проверить `ObjectType()` и использовать платформенные функции `ArrayCount`, `ArrayOptFirstElem`, `ArraySelect`, `ArrayExtract`, `ArrayRange` и другие документированные операции.

```javascript
for (elem in XQuery(xquery))
{
    // elem — очередное значение результата, а не индекс массива.
}
```

## 5. Помнить о двойственной природе XML-полей

**Официально:** поле XML-документа является объектом, но может иметь скалярное значение. В сравнении, арифметике и преобразовании к строке платформа может использовать это скалярное значение.

Не превращать XML-элемент автоматически в обычный JS-объект и не ожидать JS-прототипов. Для границ API лучше явно применять `String`, `OptInt`, `OptReal`, `OptDate` или специализированную сериализацию.

## 6. Идентификаторы WebTutor могут быть больше безопасного JS Number

**Проверенная практика:** встречаются целочисленные ID вида `9007199254740993`, которые превышают `Number.MAX_SAFE_INTEGER` стандартного JavaScript.

- В SP-XML использовать `Int`/`OptInt` и не переводить ID в `Real`.
- При передаче во внешний JavaScript/JSON сохранять ID строкой, если принимающая сторона не поддерживает 64-битные целые.
- Не выполнять над ID арифметику и не округлять их.

## 7. XQuery в SP-XML — узкое расширенное подмножество

**Официально:** для эффективного исполнения рекомендуется форма `for ... in <catalog> [where ...] [order by ...] return ...`. Это не полный W3C XQuery и не SQL.

- Не переносить произвольный синтаксис XPath/XQuery из сторонних реализаций.
- Строковые литералы вставлять через `XQueryLiteral()`, числа — после `OptInt()`/`OptReal()`.
- Не угадывать имена полей каталога. Для SQL сначала использовать read-only capability структуры таблиц, объявленную текущим репозиторием.
- Сложный SQL отчёта сначала проверять через объявленную репозиторием read-only SQL capability, затем запускать полный тест агента/отчёта.

## 8. Документ — не plain object, сохранение не автоматическое

**Проверенная практика:** документ открывается платформенными функциями, данные находятся в `TopElem`, дочерние элементы получаются методами XML-формы, а запись фиксируется `Save()`.

```javascript
var objectID = OptInt(id);
if (objectID == undefined)
    throw Error("Некорректный идентификатор");

var doc = tools.open_doc(objectID);
doc.TopElem.comment = value;
doc.Save();
```

Если в текущем серверном контексте доступен объект `tools`, в проверенной практике
предпочитать `tools.open_doc(id)`: обёртка принимает ID документа напрямую.
`OpenDoc(UrlFromDocID(Int(id)))` использовать в контексте без `tools` либо
когда такую форму требует существующий контракт.

Перед записью проверять тип документа, обязательные поля и контекст исполнения. Не считать присваивание plain object эквивалентом сохранения записи WebTutor.

## 9. Использовать библиотечную модель платформы

**Официально:** SP-XML ориентирован на библиотеки с разделением локальных и глобальных переменных. В проверенной практике библиотеки загружаются через `OpenCodeLib(UrlAppendPath(...))`.

Предпочитать существующую библиотеку из `libs/` дублированию функций внутри агента. Не заменять платформенные URL обычными путями файловой системы.

## 10. Учитывать контекст исполнения

`Param`, `CurRequest`, `SCOPE_WVARS`, `AppConfig`, `CurAuthObject`, `DefaultDb` и другие глобальные объекты доступны не во всех типах сценариев одинаково. Агент, remote action, remote collection и серверный обработчик имеют разные входы и окружение.

Проверять существующий шаблон того же типа и тестировать через соответствующую команду, объявленную текущим репозиторием.

## 11. Не изобретать функции WebTutor

Похожее имя не означает существование API. Если функция отсутствует в этом справочнике:

1. поискать ее на официальном сайте;
2. проверить применение в репозитории;
3. подтвердить сигнатуру и возвращаемый тип;
4. только затем использовать и запустить тест WebTutor.

## Финальная самопроверка

- Нет ли в коде неподтвержденного современного JS?
- Нет ли внутри тел циклов объявлений `var`, включая вложенные ветки и
  `try`/`catch`/`switch`?
- Все ли значения `undefined`, `null`, `""`, `0`, `false` обработаны явно?
- Не перепутаны ли байты и символы?
- Понятен ли фактический `ObjectType()` коллекций и XML-значений?
- Все ли внешние значения экранированы перед XQuery/SQL?
- Проверена ли схема таблицы/каталога, а не угадана?
- Не потеряется ли точность 64-битного ID?
- Используются ли документированные функции и правильный контекст исполнения?
- Запущен ли контекстный тест, объявленный текущим репозиторием?

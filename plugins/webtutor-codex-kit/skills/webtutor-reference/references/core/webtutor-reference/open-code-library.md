# Динамические библиотеки v2 через `OpenCodeLibrary()`

`OpenCodeLibrary(url)` динамически загружает из одного файла библиотеку v2 и
возвращает объект, через который доступны ее функции и переменные. Официальная
карточка отдельно предупреждает, что указанный в файле `namespace` при такой
загрузке игнорируется и что динамическая библиотека должна быть описана одним
файлом: [OpenCodeLibrary()](http://docs.datex.ru/article.htm?id=7172076235998782865).

В рабочем коде репозитория-источника и в установленной кодовой базе WebTutor
примеров вызова `OpenCodeLibrary()` не найдено. Описанное ниже поведение
подтверждено изолированным runtime-тестом проверенной версии и пока не является
сложившейся практикой проекта.

## Что показывает `spxml_web/main.js`

Поставленный файл `WebSoftServer/spxml_web/main.js` содержит реализацию модели
v2-библиотек для `spxml_web`:

- `JsCodeCollection__OpenCodeLibrary()` при каждом вызове создает новый
  `JsCodeLibrary`, вызывает `LoadFromUrl()` и возвращает объект без добавления
  в глобальную коллекцию зарегистрированных библиотек;
- конструктор `JsCodeLibrary` создает собственные коллекции `properties`,
  `methodDeclarations` и `classDeclarations`;
- `LoadFromUrl()` принимает файлы `.bs`, `.js` и `.xmi`;
- парсер сохраняет имя из `namespace` во внутреннем поле библиотеки, но только
  отдельный `RegisterCodeLibrary()` добавляет библиотеку в реестр, доступный
  через `GetOptCodeLibrary()`;
- `ProcessCode()` допускает декларации переменных, функций и классов, а также
  служебные литералы `META:`;
- `JsCodeLibraryEnv()` добавляет объект библиотеки в область разрешения имен и
  устанавливает его как `this`, что объясняет доступ методов к состоянию
  конкретного экземпляра.

Эта реализация подтверждает объектную модель, наблюдаемую в серверном тесте,
но не заменяет проверку в `xHttp_64`: `spxml_web` и серверный native runtime
могут расходиться. В частности, в `main.js` реализовано создание class-объекта,
тогда как серверный эксперимент проверенной версии завершил процесс при выполнении
`new Counter(...)`.

## Подтвержденный минимальный контракт

Библиотека может содержать переменные и функции:

```javascript
namespace ExampleLibrary {

var counter = 0;

function increment()
{
    counter += 1;
    return counter;
}

}
```

Загрузка и вызов выполняются через возвращенный объект. URL ниже является
параметром текущего репозитория, а не путём из plugin core:

```javascript
var libraryUrl = "x-local://wt/web/<custom_root>/<library_path>.bs";
var first = OpenCodeLibrary(libraryUrl);
var second = OpenCodeLibrary(libraryUrl);

first.increment(); // 1
first.increment(); // 2
second.increment(); // 1: состояние экземпляров независимо
```

Для общего контракта `OpenCodeLibrary()` подтверждено следующее; `verified_on`
фиксирует происхождение runtime-проверки, а не ограничивает правило одной
версией:

- `ObjectType()` возвращенного значения равен `BmObject`;
- функции вызываются как методы возвращенного объекта;
- переменные доступны через объект, изменяемы и сохраняют значение между
  вызовами методов одного экземпляра;
- два вызова `OpenCodeLibrary()` для одного URL создают независимое состояние;
- файл без конструкции `namespace` также загружается;
- типизированный параметр `value: string` преобразовал число `42` в строку
  `"42"`;
- лишний аргумент вызывает ошибку `Too many parameters passed to method`;
- динамическая загрузка не регистрирует библиотеку глобально:
  `GetOptCodeLibrary("<library_name>")` вернул `undefined` до и после
  загрузки;
- исполняемое выражение верхнего уровня отклоняется с ошибкой
  `Code library may contain only function or variable declarations`.

## Ограничение библиотек v1 через `OpenCodeLib()`

Общее правило совместимости для `OpenCodeLib()`: загружаемый `.js`-файл должен
содержать на верхнем уровне только объявления функций. Глобальная переменная,
включая объект конфигурации вида `var CONFIG = {...}`, приводит к ошибке:

```text
Code library may contain only function declarations
```

Рабочее решение — перенести константы и изменяемые значения внутрь функций
либо передавать их аргументами. Поведение подтверждено в контексте ASP
пользовательского веб-шаблона: после удаления глобальной переменной библиотека
успешно загрузилась через `OpenCodeLib()` и backend вернул результат.

## Кэширование исходника `OpenCodeLib()`

### Симптом

После изменения уже загруженного `.js`-файла `OpenCodeLib(url)` продолжает
возвращать старую реализацию до перезапуска `xHttp_64`. На production это
вынуждает либо перезапускать сервер, либо публиковать копию библиотеки под новым
URL.

### Установленное поведение

В изолированном runtime-эксперименте версии из `verified_on` первая загрузка
`OpenCodeLib(url)` добавила объект типа `XmFormElem` в кэш форм. Наличие объекта
проверялось документированной функцией `GetOptCachedForm(url)`. После изменения
файла на диске повторный `OpenCodeLib(url)` возвращал старую функцию из этого
объекта.

Параметр `CODE-CACHE` в `xHttp.ini` не управляет свежестью исходника
`OpenCodeLib()`: одинаковое поведение воспроизведено после отдельных запусков
сервера с `CODE-CACHE: 1` и `CODE-CACHE: 0`.

| Вызов после изменения файла без перезапуска | `CODE-CACHE: 1` | `CODE-CACHE: 0` |
|---|---|---|
| `OpenCodeLib(url)` | старая реализация | старая реализация |
| `OpenCodeLib(url + "?v=...")` | старая реализация | старая реализация |
| `OpenCodeLibrary(url)` | новая реализация | новая реализация |

Запрос с `?v=...` не создает новый ключ: `GetOptCachedForm()` возвращает форму с
базовым URL без query-параметра.

`DropFormsCache()` в этой версии также не сбросила псевдоформу библиотеки v1.
Проверены два ограниченных варианта аргумента: маска, ограниченная точным
лабораторным каталогом, и полный `x-local://...` URL библиотеки.

В обоих случаях вызов завершился без исключения, но `GetOptCachedForm()`
продолжил возвращать тот же `XmFormElem`, а `OpenCodeLib()` — старую функцию.
Это согласуется с диагностической строкой ядра
`DropFormsCache function is obsolete`. Широкий вызов `DropFormsCache("*")` не
проверялся и не должен использоваться для эксперимента на рабочем сервере.

Настройка портала «Тип кеширования шаблонов» и кнопка «Сбросить кеш шаблонов»
относятся к объектам `active_web_template`; они не являются способом очистки
кэша `OpenCodeLib()`.

### Рабочие варианты обновления

Для библиотеки v1 подтверждены только перезапуск процесса `xHttp_64` либо новый
URL файла. Если библиотека содержит только совместимые объявления функций,
кандидат на решение без перезапуска — загрузка того же `.js` через
`OpenCodeLibrary(url)`: в эксперименте она вернула объект `BmObject` и прочитала
измененный файл заново. Это не механическая замена API: перед миграцией каждой
библиотеки нужно проверить способ вызова, состояние, допустимые декларации и
контекст исполнения.

Точное назначение native-параметра `CODE-CACHE` этим экспериментом не
установлено. Установлена только его неприменимость для инвалидации исходника
`OpenCodeLib()`.

## Границы безопасного применения

Общий безопасный контракт рассматривает `OpenCodeLibrary()` как способ создать
отдельный объект-модуль из одного файла с функциями и состоянием. `verified_on`
сохраняет provenance исходного эксперимента; перед использованием в новом
контексте исполнения всё равно нужен отдельный runtime-тест.

Не переносить существующие библиотеки с `OpenCodeLib()` автоматически:
попытка открыть namespaced v2-файл через `OpenCodeLib()` завершилась штатной
ошибкой `Code library may contain only function declarations`.

Не использовать классы внутри динамической библиотеки без отдельного
compatibility-теста. В версии из `verified_on` сам файл с декларацией `class`
загрузился, но выполнение фабричной функции с
`new Counter(...)` дважды завершило процесс `xHttp_64` и оборвало HTTP-запрос.
Авария повторилась как с типом результата `: Counter`, так и без него. После
обновления WebTutor это ограничение нужно проверить заново на изолированном
стенде.

Документированная вспомогательная функция `CodeLibraryMethodExists()` в
проверенном серверном контексте не определена. Не использовать ее без отдельной
проверки доступности в нужной версии и контексте.

Не проверены и не входят в установленный контракт:

- `RegisterCodeLibrary()` и глобально зарегистрированные библиотеки v2;
- объединение нескольких исходных файлов;
- совместное использование экземпляра параллельными запросами;
- время жизни состояния между отдельными HTTP-запросами;
- поведение при сбросе кэша в кластере или нескольких worker-процессах.

## Воспроизведение

Безопасный основной тест должен быть объявлен текущим репозиторием и выполняться на изолированном стенде. Проверить UTF-8 BOM у исполняемых серверных fixtures и не менять тестовый endpoint.

Исторический эксперимент кэширования использовал подготовленное состояние: в памяти была старая версия библиотеки, а на диске — новая. Конкретные имена лабораторных агентов и каталогов не являются переносимым контрактом.

Агенты с `class_untyped` и `class` намеренно воспроизводят завершение
`xHttp_64`; не запускать их на используемой службе WebTutor. Тестовый endpoint
для эксперимента не изменялся.

## Поиск примеров в поставке

На 2026-09-03 поиск точного вызова `OpenCodeLibrary(` по установленному
`WebSoftServer` нашел только лабораторные агенты из репозитория-источника. В коде
поставки присутствуют вызовы `RegisterCodeLibrary()` для библиотек `app_ui`, но
это другой способ подключения и он не подтверждает серверный контракт
`OpenCodeLibrary()`.
